# Анализ кода

## 1. Основная задача
1.1. Провести анализ кода на предмет соответствия изученным принципам.

1.2. Предложить свои варианты исправления.

---

## 2. Результат

---

### 2.1. Рефакторинг архитектуры

 - произведен переход от сильно связанного сервиса к многослоной рхитектуре с элементами Clean Architecture и Hexagonal Architecture
 - основной целью рефакторинга являлось разделение ответственности между слоями приложения и снижение связанности компонентов

---

### 2.2. Разделение на слои

 - проект разделен на независимые слои, что позволило изолировать бизнес-логику от деталей реализации HTTP-запросов, отображения представлений и логики проверки

 - используемые слои:

    - Application
    - Domain
    - Infrastructure  
    - HTTP
    - Shared

#### Application

 - содержит сценарии использования приложения

 - класс:

  - ValidateEmailsUseCase: отвечает за выполнение бизнес-сценария проверки списка электронных адресов


#### Domain

 - содержит основную бизнес-логику приложения

 - классы:

    - EmailValidator
    - EmailValidationRuleInterface
    - ValidationResult
    - ValidationMessages

 - слой не зависит от HTTP, контейнера зависимостей и пользовательского интерфейса


#### Infrastructure

 - содержит технические реализации и внешние зависимости

 - классы:

    - Container
    - EmailValidation
    - MxValidation
    - Views

 - отвечают за создание объектов приложения и взаимодействие с внешними механизмами проверки

#### HTTP

 - содержит входную точку взаимодействия пользователя с приложением

 - класс:

    - EmailController

 - отвечает за обработку HTTP-запросов и передачу данных в слой Application

#### Shared

 - сдержит вспомогательные компоненты общего назначения

 - классы:

    - RequestParser
    - ResponseParser
    - RequestMessages

### 2.3. Применение изученных принципов:

 - SOLID:

    - Single Responsibility

        - первоначальный класс EmailValidationService одновременно выполнял несколько задач:

            - получение HTTP-запроса;
            - парсинг данных;
            - выполнение валидации;
            - формирование ответа.

        - после рефакторинга обязанности разделены между специализированными компонентами:

            - RequestParser — разбор входящих данных;
            - ValidateEmailsUseCase` — выполнение сценария проверки;
            - ResponseParser — формирование HTTP-ответа;
            - EmailController — координация HTTP-взаимодействия.
    
    
    - Open/Closed: добавление новых проверок теперь не требует изменения существующего кода. Можно создать новый класс, реализующий EmailValidationRuleInterface, и добавить его в контейнер (Container.php)

    - Liskov Substitution Principle: все реализации интерфейса EmailValidationRuleInterface могут свободно заменять друг друга без изменения поведения системы

    - Interface Segregation Principle: интерфейс содержит только один специализированный метод public function check(string $email): ValidationResult, что исключает наличие неиспользуемых зависимостей

    - Dependency Inversion: классы высшего уровня (EmailController, ValidateEmailsUseCase) больше не создают свои зависимости самостоятельно. Они зависят от внедряемых сервисов, которые передаются через конструктор с помощью DI (класс Container)

 - DRY: тексты ошибок вынесены в Enum (ValidationMessages, RequestMessages). Исключено дублирование строк по всему коду. Код генерации HTTP-ответов сконцентрирован в ResponseParser

 - KISS: использование match в ядре и отсутствие переусложненных абстракций в парсерах делает код легко читаемым

 - YAGNI: из проекта удалена лишняя абстракция EmailValidatorFabric, так как класс не создавал новые объекты и фактически не являлся фабрикой. После рефакторинга он был заменён на более простой класс EmailValidator, что позволило уменьшить сложность архитектуры без потери функциональности

 ---

 ### 2.4. Использование паттернов проектирования:

  - IoC Container: реализован в виде класса Container, который отвечает за разрешение и внедрение зависимостей, освобождая бизнес-логику от необходимости знать, как создавать объекты

  - Strategy: класс EmailValidator использует массив объектов EmailValidationRuleInterface. Поведение валидации изменяется динамически в зависимости от переданных стратегий (правил EmailValidation и MxValidation)

  - Chain of Responsibility: класс EmailValidator реализует последовательное выполнение цепочки проверок. Каждое правило получает адрес электронной почты и может передать управление следующему обработчику или остановить выполнение цепочки при обнаружении ошибки. Это позволяет легко расширять набор правил проверки без изменения существующего кода

  - Data Transfer Object: класс ValidationResult используется исключительно для инкапсуляции и передачи результатов валидации между слоями (из Domain в Application), не содержа в себе бизнес-логики

  - Facade: класс Views предоставляет простой интерфейс (один статический метод) к более сложной подсистеме поиска, валидации путей и рендеринга HTML-шаблонов
