# Вводные условия

Тестируем бэк для страницы оплаты просмотра фильма через платёжный сервис A.

В системе взаимодействуют четыре модуля: фронт, бэк, репозиторий, платёжный сервис A.

Принятое поведение фронта:

- при ошибках валидации (`400`) - подсвечивает конкретное поле красной рамкой с сообщением;
- при ошибке списания (`403`) - показывает «Не удалось списать деньги с карты, проверьте реквизиты»;
- при технических ошибках - показывает «Произошла техническая ошибка, попробуйте позже».

---

## 1. Модульные тесты

Тестируем бэк изолированно. Сервис A и репозиторий заменяются моками.

### 1.1. Валидация `card_number`

Невалидные случаи (`400`):
- поле отсутствует;
- пустое значение;
- меньше 16 цифр;
- больше 16 цифр;
- содержит нецифровые символы.

Валидный случай:
- ровно 16 цифр.

### 1.2. Валидация `card_holder`

Невалидные случаи (`400`):
- поле отсутствует;
- пустое значение;
- содержит не латиницу, цифры или недопустимые спецсимволы;
- только одно слово;
- лишние пробелы.

Валидные случаи:
- `IVAN IVANOV`;
- `ANNA-MARIA IVANOVA`.

### 1.3. Валидация `card_expiration`

Невалидные случаи (`400`):
- поле отсутствует;
- пустое значение;
- неверный формат;
- месяц `00` или больше `12`;
- дата в прошлом.

Валидный случай:
- текущий месяц или будущая дата в формате `мм/гг`.

### 1.4. Валидация `cvv`

Невалидные случаи (`400`):
- поле отсутствует;
- пустое значение;
- не ровно 3 цифры.

Валидный случай:
- ровно 3 цифры.

### 1.5. Валидация `order_number`

Невалидные случаи (`400`):
- поле отсутствует;
- пустое значение;
- длина больше 16 символов.

Валидные случаи:
- до 16 произвольных символов (например `ORDER-2026-0001`);
- одиночный символ (`A`).

Edge-case на безопасность:
- значения вида `<script>x`, `' OR 1=1--` — ожидаем `400` (whitelist `[A-Za-z0-9_-]`), чтобы исключить XSS и SQL-инъекции.

### 1.6. Валидация `sum`

Невалидные случаи (`400`):
- поле отсутствует;
- пустое значение;
- неверный формат;
- ноль или отрицательное значение.

Валидный случай:
- корректная строка (`100,50`) преобразуется в `float(100.50)`.

### 1.7. Логика оплаты

Позитивный сценарий:
1. На вход: все поля валидны, `order_number=ORDER-1`, `sum=100,50`.
2. Бэк вызывает сервис A с суммой `float(100.50)`.
3. Сервис A возвращает `200`.
4. Бэк вызывает `setOrderIsPaid(orderNumber, sum)`, репозиторий возвращает `true`.
5. Бэк отвечает `200`.

Негативные сценарии:
- При невалидных данных сервис A и репозиторий не вызываются.
- Если сервис A возвращает `403`, бэк возвращает ошибку списания, репозиторий не вызывается.
- A недоступен → бэк возвращает `500`, репозиторий не вызывается.
- `setOrderIsPaid()` выбрасывает исключение или возвращает `false`, бэк возвращает техническую ошибку (`500`).

## 2. Интеграционные тесты

Проверяем взаимодействие двух модулей, остальные заменяются моками.

### 2.1. Связка «фронт - бэк»

1. Невалидное поле (например `card_number` из 15 цифр) - бэк возвращает `400`, фронт подсвечивает соответствующее поле красной рамкой.
2. Бэк возвращает `403` - фронт показывает общую ошибку оплаты.
3. Все поля валидны - фронт формирует корректный JSON, бэк не возвращает ошибку валидации.

### 2.2. Связка «бэк - сервис A»

1. Сервис A возвращает `200` - бэк переходит к записи через репозиторий (мок репозитория фиксирует вызов).
2. Сервис A возвращает `403` - бэк возвращает ошибку, репозиторий не вызывается.
3. Сервис A недоступен - бэк возвращает техническую ошибку, репозиторий не вызывается.

### 2.3. Связка «бэк - репозиторий»

1. После `200` от сервиса A бэк вызывает `setOrderIsPaid()` с корректными `order_number` и суммой в виде `float`.
2. `setOrderIsPaid()` возвращает `true` - бэк возвращает успешный ответ.
3. Репозиторий выбрасывает исключение - бэк возвращает ошибку, пользователь не получает подтверждения оплаты.

---

## 3. Системные тесты

Все четыре модуля работают вместе. Сервис A заменяется sandbox-режимом.

1. Пользователь вводит валидные данные, существующий заказ и верную сумму - оплата проходит, в БД появляется запись, фронт показывает сообщение об успехе.
2. Пользователь вводит неверный `cvv` - сервис A возвращает `403`, фронт показывает «Не удалось списать деньги с карты, проверьте реквизиты», заказ не отмечается оплаченным.
3. Пользователь вводит просроченную дату - бэк возвращает `400`, фронт подсвечивает поле, запрос в сервис A не отправляется.
4. Пользователь вводит валидную карту, но номер заказа отсутствует в БД - сервис A возвращает `200`, репозиторий выбрасывает исключение, фронт показывает техническую ошибку, заказ не считается оплаченным.

---

## 4. Как удешевить тестирование

- Добавить mock-объекты сервиса A и репозитория чтобы не было реальных запросов.
- Добавить тестовые заглушки сервиса A и тестовая БД.
- Добавить sandbox-режим платёжного сервиса с тестовыми картами.
